## What changed

0.1.0 was generated by a UE 4.27 editor commandlet (BPForge) from a Python spec, then cooked in an FSD-Template
project. This branch replaces that with C++ that [AssetGen](https://github.com/Elytras/CPP-to-blueprint-compiler)
compiles straight to cooked assets: `Mod/DwarfBuilds`, one header per Blueprint, built by `Mod/mods.yaml`.

The sources started as AssetGen's `bpdecomp.py` output of the 0.1.0 pak and were then edited by hand:

- `DB_Mod` (the shared body of `InitSpacerig` and `InitCave`) is rewritten. It bound the open key as an input key
  (`UE_INPUT_KEY("AnyKey", ...)`, as 0.1.0 cooked it) until the window moved to the Mod Hub menu (below).
- `ModHub.h` declares the Mod Hub interfaces this mod uses, so it builds without Mod Hub's sources.
- SDK spellings (`playerID`, `Upgrades`, `Name_0`, `isEmpty`) and enum constants in place of raw integers.
- `DB_TakeDialog`: the "equip after saving" checkbox holds its row through an overlay, because AssetGen cannot yet
  tell the slot class of a `UCheckBox`'s content. It looks and behaves as before.

## Performance fixes

- `DB_Window` roster: the strip is rebuilt only when the players, their classes or names, or the page change.
- `DB_Column.ShowPlayer`: returns early when the player, class, name, level, loadout, perks and stats are what it
  last drew (re-drawn at least every 10 s anyway).
- Class selection: `SelectPoll` (0.5 s, which in 0.1.0 ran for the whole level and scanned every widget until the
  screen appeared) now stops once the overlay is attached, or 60 s after BeginPlay or the game's selection start
  (3 s after a game window opens, from upstream 0.2.0). The overlay then refreshes itself from its own tick, once a
  second while shown.

## What other players' builds come from

What a machine can see of another player, checked with three copies of the game on one PC (localmp, 2026-11-22):

- Upgrades and overclocks: each player's `SaveGameStateComponent.ItemUpgradeSelections` replicates to everyone, but
  it holds only what that player's game last sent the host. The host's own is there from the start; a client's
  stays empty on the host until the client's game sends its loadout (after class selection), and goes stale when the
  host changes loadouts without sending one. That stale host entry is the "host's upgrades mostly missing" a client
  saw on 0.1.0.
- Perks: `EquippedPerks` does not replicate at all. The host has a client's only when the client's game sends them,
  which it had not done on the space rig in any test. So a client never sees another player's perks from the game,
  and 0.1.0's perk table (`DB_PerkShare_v1`) could only pass on the host's own: the empty perk rows of the other
  clients.

So this build adds `DB_BuildShare_v2`, one actor per player, which the host spawns owned by that player's controller.
Each player's own copy of the mod sends its full build code (upgrades, overclocks, perks) through its actor
(`Server_SetCode`), and the host replicates every actor to everyone. A player without the mod keeps an empty actor
and is shown from what the game replicates (the host filled it in until upstream 0.2.0 dropped that); perks nobody
has show as "Not available. The game does not share this player's perks." instead of an empty row. With a host that does not run this build, clients fall back to 0.1.0's sources: the
replicated selections for builds, the host's perk table for perks, or "not available".

[Build Inspector](https://mod.io/g/drg/m/build-inspector) (AssemblyStorm) was checked for a better source. Its
assets are in [trumank/drg-mods](https://github.com/trumank/drg-mods) (`Content/_AssemblyStorm/BuildInspector`), MIT
licensed (Copyright (c) 2022 Truman Kilen). Its `LoadoutData::BuildFromPlayerState` reads the same replicated
`ItemUpgradeSelections`, first entry per slot, as 0.1.0 does, and shows no perks of other players. Nothing was taken
from it.

## A page in Elytras Mod Manager's hub

The window has no key of its own any more (no `DB_Settings.OpenKey`, no `UE_INPUT_KEY`, no key picker). A 0.1.0
settings save still holds `OpenKey`; loading skips it.

The Mod Hub API has no "menu entry" call: a hub lists every actor implementing `IHubMod` and shows the pages its
`GetModPages` returns. `DB_Hub` is that actor and `DB_Window` its one page.

`DB_Window` is a native EMM page (`IHubPageWidget` and EMM's `IHubLook`), laid out to the hub's pane in EMM's widgets,
the way EMM's own pages and DescriptorViewer's are (`ue-mods/BpMods/ElytrasModManager/HUB.md`, "IHubLook"):

- A top row of `BasicButton`s: the Team and Build code tabs (`PageTab`, selected), Browse builds, and the player
  count. Past four players, a row of class filters ("All 5", "Driller 2", ...). No frame, title bar, logo or close.
- Team: one card (`DB_Column`) per shown player, in a wrap box from the top of the pane, as many to a row as its width
  holds, scrolled down past that. A card is 900 wide: the player line, the two weapons side by side, the four gear
  boxes in one row, perks, buttons. Cards are made as players show and kept. The roster chips and the four-column
  paging of the old window are gone (`DB_Chip` deleted).
- No text in a card clips in the hub's font (the user, 2026-11-24: the class line, overclock names and section
  titles were cut). The game's condensed fonts had fixed-height boxes and negative paddings tuned to them; now every
  text row's size box is a minimum height, the negative paddings are 0, names wrap (player, class line, weapon,
  category, overclock, gear), and the card, weapon and gear boxes are as tall as their text.
- Build code: the code box (a single-line `UEditableTextBox` in the hub's style), its status, Paste from clipboard,
  Take this build, Copy my code, Publish my build, Open in browser, and the preview column beside them. The take
  dialog (`DB_TakeDialog`) covers the page while open; Escape closes it, else goes on to the hub.
- `ApplyLook` (each time the hub shows the page) gives the code box the hub's text box style and takes its text colour
  (the palette's Text) for the page's labels, which take the hub's font. Columns, the preview and the take dialog keep
  their game icons and class colours; their panels take the hub's field style (`StyleField`), their buttons the
  hub's flat look with the orange bars hidden (`RestyleForeign` on the button alone, so the cards' hover buttons keep
  theirs), their labels the hub's font (`StyleColumn`). EMM's `Widget` service exports no getter for a tint
  (`StyleOf` is not in the UeApi), hence the text box as the source of the Text colour.
- `HubPageOpened` finds this world's `DB_Data` and opens the page every time it shows (once-a-second refresh while
  shown); `HubPageClosed` stops it. With no `DB_Data` (not on the Space Rig or in a mission) the count line says so.

The page imports EMM's classes (`BasicButton`, `IHubLook`, the `Widget` service), so it needs EMM: `DB_Mod` spawns
`DB_Hub` only when `/Game/_ElytrasMods/Manager/Core/Services/Widget/IHubLook` loads (EMM carries Mod Hub's
interfaces too). With Mod Hub from mod.io and no EMM there is no page. Building needs a UeApi with EMM's headers:
ue-mods' `BpMods/UeApi`.

History: until 2026-11-23 the page held an OPEN DWARF BUILDS button that opened the old `UWindowWidget` over the hub
(the user: not wanted). Then the window sat inside the page (`feat/hub-embed`), which the user called a menu inside a
menu (2026-11-24). This page replaces both.

Seen in drgq: job `20261124-031216-dwarfbuilds-emm-page` (74fbef7) showed the page with one 418-wide card, clipped
text, centred under an empty band. With the card fix, job `20261124-191629-dwarfbuilds-emm-card` (01bc071, solo, Space
Rig): one 900-wide card at the top of the pane, no text cut (the class line, "Electrocuting Focus Shots" and "High
Caliber Rounds" on two lines, "UNSTABLE OVERCLOCK" whole, "Grappling Hook" and "Armor Rig" with their descenders), the
same after closing and opening the hub; Build code with your own code pasted shows "Valid code: SCOUT BUILD" and the
preview card, which sat centred under a gap and is pinned to the top since. Not checked: several players in the wrap
box, a pane narrower than a card, a lobby.
`ModHub.h` declares the interfaces with `UE_COOKED`. Without it AssetGen cooked them, since a header in the mod's
own folder counts as the mod's, and every build until now shipped its own `/Game/_ModHub/IHub*.uasset` stubs. Those
could stand in for the hub's real interfaces, and made DB_Mod's "is a hub installed" check always pass.

## Network compatibility

`Mod/netcontract.json` pins both replicated classes, as upstream 0.2.0 ships them (above). `DB_PerkShare_v1` is exactly as 0.1.0 shipped it: class path,
`Actor` super, and the five arrays `Classes`, `Counts`, `Ids`, `Perks`, `Ranks`. `DB_BuildShare_v2` is new: `Player`,
`Code`, `PerksKnown`, `FromPlayer` and the reliable `Server_SetCode(NewCode)`. AssetGen's `bpbuild.py` refuses to
pack a build whose surface drops or changes any of it (`netsurface.py`).

A client that lacks a replicated class (0.1.0, or no mod) logs "SerializeNewActor failed to find/spawn actor" and
tells the server, which stops sending it that actor (UE 4.27 `UActorChannel::ProcessBunch`,
`NMT_ActorChannelFailure`); the connection stays up.

Checked with localmp (host and two clients on one PC, space rig):

- Host and client A on this build, client B without the mod: A sees the host's and its own builds with perks, and B
  as far as the host knows B (perks "not available"); the host sees A's build with perks; B stays connected.
- Host without the mod, client A on this build: A sees the host's build from the replicated selections, perks "not
  available, the host does not run this mod".
- Host on this build, a client on 0.1.0: the 0.1.0 client sees the host's perks through `DB_PerkShare_v1` and stays
  connected; a client on this build sees everyone through `DB_BuildShare_v2`.

Not checked: two real machines over Steam, and a client whose game has sent its loadout after class selection (the
test copies stayed on the selection screen).
